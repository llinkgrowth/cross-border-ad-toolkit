# 一条链接分给 5 个客服：加权路由怎么实现（附伪代码）

> 一句话结论：分流短链的难点不是「随机分」，而是**同一个客户永远落到同一个客服**，同时还能按权重调人、有人掉线时自动兜底。

一个 WhatsApp 号接不住五个客服，是出海团队最常见的浪费：客户发来消息，谁先看到谁回，结果有人回三遍，有人一条没回；客户等二十分钟，走了。

直觉方案是「轮询」：第 1 个客户给 A，第 2 个给 B，第 3 个给 C。它实现只要十行代码，但会在三个地方翻车：同一个客户第二次点进来换了人、客服请假权重调不了、某个号挂了继续往那分。下面按「需求 → 三种算法 → 生产实现 → 测试」拆开写。

## 一、先把需求写成四条

1. **公平**：权重 3:2:1 时，长期分配比例要接近 3:2:1。
2. **粘性**：同一个访客（同一设备/浏览器）重复点击，必须回到同一个客服；否则对话上下文全丢。
3. **可调**：有人请假、有人加进来，改权重后老客户尽量不动。
4. **可观测**：每次点击落到谁、有没有兜底，要能查；否则没法对账。

这四条互相打架：越随机越公平，越粘性越不随机；权重一变，哈希桶全乱。所以生产上通常是「**粘性优先 + 加权兜底**」。

## 二、三种算法，从错到对

### 1. 轮询（Round Robin）：只适合发传单

```
counter = 0
function pick(targets):
    target = targets[counter % len(targets)]
    counter = counter + 1
    return target
```

问题：客户第二次来，counter 已经变了，落到别人；多实例部署时 counter 不共享；权重无法表达。**只适合一次性活动，不适合客服接待。**

### 2. 加权随机（Weighted Random）：公平，但不粘

```
function pick(targets):
    total = sum(t.weight for t in targets)
    r = random() * total
    acc = 0
    for t in targets:
        acc = acc + t.weight
        if r < acc: return t
```

问题：同一个客户每次都可能换人；权重调整后比例立刻变，但粘性为零。**可以当兜底策略，不能当主策略。**

### 3. 粘性哈希（Sticky Hash）：主线方案

思路：给每个访客一个稳定 ID（cookie 或指纹），把 ID 哈希到一个固定区间，再把区间按权重切给客服。

```
function pick(visitorId, targets):
    available = filter(targets, enabled and weight > 0)
    if empty(available): return null

    # 1) 先看有没有粘性记录
    route = cookie.get("route")
    if route in available: return route

    # 2) 没有记录，按权重哈希
    total = sum(t.weight for t in available)
    bucket = hash(visitorId + ":v1") mod 10000
    acc = 0
    for t in available:
        acc = acc + t.weight / total * 10000
        if bucket < acc: 
            cookie.set("route", t.id, maxAge=7d)
            return t
```

优点：同一访客稳定；权重按比例分；实现短。缺点：**权重一变，所有桶重新切**，老客户会漂移（第 3 条需求做不到）。

### 4. 一致性哈希（Consistent Hashing）：改权重只动一小部分

把客服节点（含虚拟节点）放到一个哈希环上，访客哈希后顺时针找第一个节点：

```
ring = []
for t in targets:
    for i in 0..virtualNodes(t):
        ring.push({ hash: hash(t.id + ":" + i), target: t })
sort(ring by hash)

function pick(visitorId):
    point = hash(visitorId + ":v1")
    node = first node in ring with hash >= point, else ring[0]
    return node.target
```

改权重时只增减虚拟节点，受影响的只是相邻区间；但实现比加权哈希复杂，且**小样本下分布会有偏差**。5 个客服的规模，用「加权哈希 + 粘性 cookie + 失败重算」就够了；到几百个接待再上一致性哈希。

## 三、生产实现：Cloudflare Worker（约 60 行）

> 这一段是真实可跑的代码，不是伪代码。配置放环境变量，目标列表不要写死在代码里。

```js
// worker.js —— 粘性优先 + 加权兜底 + 失败重算
const COOKIE_VID = "vid";
const COOKIE_ROUTE = "route";
const ONE_YEAR = 60 * 60 * 24 * 365;
const ONE_WEEK = 60 * 60 * 24 * 7;

function fnv1a(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}

function getCookie(req, name) {
  const raw = req.headers.get("Cookie") || "";
  const hit = raw.split(";").map(s => s.trim()).find(s => s.startsWith(name + "="));
  return hit ? decodeURIComponent(hit.slice(name.length + 1)) : null;
}

export function pickTarget(visitorId, targets) {
  const available = targets.filter(t => t.enabled && t.weight > 0);
  if (available.length === 0) return null;

  const total = available.reduce((s, t) => s + t.weight, 0);
  const bucket = fnv1a(visitorId + ":v1") % 10000;
  let acc = 0;
  for (const t of available) {
    acc += (t.weight / total) * 10000;
    if (bucket < acc) return t;
  }
  return available[available.length - 1];
}

export default {
  async fetch(req, env) {
    const targets = JSON.parse(env.TARGETS_JSON || "[]");
    const available = targets.filter(t => t.enabled && t.weight > 0);
    if (available.length === 0) {
      return new Response("No available agents", { status: 503 });
    }

    const visitorId = getCookie(req, COOKIE_VID) || crypto.randomUUID();
    const stickyId = getCookie(req, COOKIE_ROUTE);
    const sticky = available.find(t => t.id === stickyId);

    const target = sticky || pickTarget(visitorId, available);
    if (!target) return new Response("No available agents", { status: 503 });

    const headers = new Headers({ Location: target.url });
    headers.append("Set-Cookie", `${COOKIE_VID}=${encodeURIComponent(visitorId)}; Path=/; Max-Age=${ONE_YEAR}; HttpOnly; Secure; SameSite=Lax`);
    headers.append("Set-Cookie", `${COOKIE_ROUTE}=${encodeURIComponent(target.id)}; Path=/; Max-Age=${ONE_WEEK}; HttpOnly; Secure; SameSite=Lax`);

    // 真实环境：这里写一条点击日志（见下一节的表结构），不要阻塞跳转。
    // env.CLICKS.write({ targetId: target.id, visitorId, ts: Date.now(), url: req.url });

    return new Response(null, { status: 302, headers });
  }
};
```

配置示例（`TARGETS_JSON`）：

```json
[
  { "id": "a", "url": "wa.me/10000000001", "weight": 3, "enabled": true },
  { "id": "b", "url": "wa.me/10000000002", "weight": 2, "enabled": true },
  { "id": "c", "url": "wa.me/10000000003", "weight": 1, "enabled": true }
]
```

> 注意：`Location` 必须是绝对地址，部署时把 `wa.me/...` 补成完整的协议 + 域名。示例里省略协议，是为了让本文能原样分发。

## 四、数据要不要落库

不落库也能跑，但「谁接的、点了几次」就查不到。最小表结构：

```sql
-- 分配记录：一个访客只应有一条有效记录
CREATE TABLE assignments (
  visitor_id TEXT PRIMARY KEY,
  target_id  TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

-- 点击流水：只追加，不更新
CREATE TABLE clicks (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  visitor_id TEXT NOT NULL,
  target_id  TEXT NOT NULL,
  ts         INTEGER NOT NULL,
  referrer   TEXT,
  country    TEXT
);
```

写入策略：**先返回 302，再异步写日志**（Workers 里用 `ctx.waitUntil` 或队列），不要让数据库抖动拖慢跳转。

## 五、测试怎么写（伪代码）

```text
test "分布接近权重":
  counts = {}
  for i in 0..10000:
    t = pickTarget("visitor-" + i, targets)   # 不带 cookie 的纯函数
    counts[t.id] += 1
  assert abs(counts.a / 10000 - 0.5) < 0.05   # 3:2:1 时 a 占 50%
  assert abs(counts.b / 10000 - 0.33) < 0.05

test "粘性":
  t1 = pickTarget("visitor-1", targets)
  for i in 0..100:
    assert pickTarget("visitor-1", targets) == t1

test "某个客服下线":
  targets_b = disable(targets, "a")
  for 1000 visitors:
    t = pickTarget(visitor, targets_b)
    assert t.id != "a"
  # 老客户会漂到其他可用客服，属于预期行为

test "权重调平后只有一部分人漂移":
  old = assign(10000 visitors, weights={3,2,1})
  new = assign(10000 visitors, weights={2,2,1})
  moved = count(visitor where old != new)
  assert moved > 0 and moved < 0.5 * 10000   # 不会全量重排
```

最后一条是「改权重别把所有人打散」的验收线；如果你的实现是简单哈希取模，这一条大概率过不了。

## 六、边界情况

- **用户禁用 cookie**：每次都会重新分配。要么接受，要么用「首次落地页 URL 带 `?v=` 参数」做兜底。
- **权重全为 0**：返回 503，不要落到默认号；否则等于没配置。
- **客服号满员**：目标里加 `enabled=false`，比改权重更安全（不会重排其他人）。
- **隐私**：只存随机 visitorId，不存手机号、不存聊天内容；日志保留期写进隐私说明。
- **别把分流当归因**：分流只保证「落到谁」，成单归因要靠后台的对账数据，别在链接上编承诺。

## 七、什么时候该买工具，什么时候自己写

- 5 个以内客服、单市场、每周改一次权重：一个 Worker + 一张表就够，代码量约 100 行。
- 多市场、多语言、几十个接待、要权限和报表：自己维护成本会超过工具费，直接用现成的分流后台更划算。
- 不管哪种，**先在测试环境跑分布和粘性测试**，再上真实流量。
