# 斗篷和分流，公开能讲的部分：入口、超时、一条链分给多人

> 一句话结论：斗篷（cloak）解决「这个访客该看哪一页」。分流解决「这条点击该落到哪个接待」。两件事都发生在入口的几十毫秒里。公开能讲的是入口怎么接、超时怎么放行、一条链怎么分人。判定名单不在这篇文章里。

投手每天碰到的是两个具体故障，不是两个抽象名词。

第一个：广告点进来的人，和你自己打开链接看到的，不是同一页。你以为页面坏了，其实是入口按访客特征选了不同去向。这个机制通常叫斗篷，也叫访问规则、流量分流。

第二个：五个客服共用一个 WhatsApp 号，谁先看到谁回。有人回三遍，有人一条没回。这不是客服懒，是一条链接没有分配。

下面只讲这两件事的公开部分。

## 一、斗篷在入口做三件事

1. 收下这次访问：IP、浏览器标识、语言、来源、链接上的点击编号。
2. 问一次远端：这个访客放行，还是换一页。
3. 按回答动作：继续原页面、在当前域名输出另一页、跳去别的地址，或返回找不到。

第三步里最重要的是超时。远端 800 毫秒没有回答，或者返回了看不懂的内容，入口必须放行，让原来的页面照常打开。宁可多放一个人，不能把整站卡死。

```text
function gate(request):
    if path is static file: return pass
    payload = collect(ip, ua, language, referer, click ids)
    answer = post(decision endpoint, payload, timeout 800ms)
    if answer failed or timed out: return pass
    switch answer.action:
        pass: return pass
        render_safe: write local page, stop
        redirect: send location, stop
        not_found: send 404, stop
```

本地可以先接一个只有两三条演示规则的假服务，把安装脚本、WordPress 钩子和超时放行跑通。真的多维判定在云端，不写在业务站的源码里。

公开可以说的词：访问规则、流量分流、超时放行、安全页兜底、同一域名输出另一页。

公开不说的：哪一类访客会被换页、名单里有哪些网络、阈值是多少。那些是运营配置，不是安装文档。

## 二、分流在入口做三件事

1. 一条短链后面挂多个目标：多个客服号，或多个语言的落地页。
2. 按规则挑一个：随机、按权重、轮流、或按今天还剩多少配额。
3. 记住这个人：同一浏览器下次再点，回到同一个接待。接待下线了，再重新挑。

```text
function pick(visitor, targets):
    alive = targets that are enabled
    if visitor has a sticky target and that target is alive:
        return sticky target
    return one of: random, weighted, round_robin, quota
    write sticky cookie for one year
```

配额模式用来防止一个号当天被加满。全满时回到第一个还能用的目标，而不是把点击丢掉。

WhatsApp、Telegram、LINE 的链接可以在挑中目标之后再拼：号码只留数字，欢迎语做编码，入口上的来源参数带到最终地址。这一步没有秘密，写错只会让客服打不开聊天窗口。

## 三、两件事可以叠在同一条链上

先分流，再斗篷，或先斗篷，再分流，取决于你要先决定「看哪页」还是先决定「找谁」。公开文档只需要把顺序写清楚：

```text
click
  -> optional cloak gate (timeout = pass)
  -> optional rotator (sticky)
  -> destination
```

统计要分开记。斗篷的放行次数不是转化。分流的点击次数也不是开口。开口要等客服真的收到第一条消息。

## 四、上线前四条

- [ ] 把判定地址改成一个不存在的端口，页面仍能在一秒内打开
- [ ] 同一浏览器连点三次，落到同一个接待
- [ ] 把那个接待标成下线，下一次点击换到别人，而不是报错
- [ ] 最终地址上还带着原来的来源参数
