# 落地页上线前检查清单 · 37 项

一份可以照着打勾的落地页上线前检查表。**37 项，7 组**，每项一句判断标准；容易翻车的地方补了「不合格怎么改」。

用法：上线前从头到尾走一遍，全绿再投。不用一次做完，先做「首屏」和「表单与 CTA」这两组，收益最直接。

> 配套可勾选版本：[`checklist.html`](./checklist.html)（带进度条、本地保存、可打印）

---

## 自动检查器（可选）· 自动 12 项 / 人工 25 项

仓库里带了一个零依赖的 Node 命令行工具 [`checker.mjs`](./checker.mjs)：上线前先跑一遍，把 37 项里**能自动判断的 12 项**过掉。

> **先说边界**：自动检查只覆盖 37 项中的 12 项（16 条规则），其余 **25 项必须人工判断**。自动检查全 PASS **不等于页面可以上线**——它不做合规审查、不判断信任内容、不代替真机走查，也不预测投放效果。

### 环境

Node.js 20 及以上；**零第三方依赖**，不用 `npm install`。测试全程不联网。

### 用法

```bash
node checker.mjs <url> [--json] [--timeout 10000] [--no-fail]
```

| 参数 | 说明 |
| --- | --- |
| `<url>` | 要检查的页面地址，必须 `http://` 或 `https://` 开头 |
| `--json` | 输出 JSON（给脚本 / CI 用），不打印表格 |
| `--timeout <毫秒>` | 请求超时，默认 `10000`（1000–120000） |
| `--no-fail` | 即使有 FAIL 也返回退出码 0（只报告，不拦截发布） |
| `--help` | 显示用法 |

跑测试：

```bash
npm test        # 等价于 node --test，35 个用例，零网络
```

本地演示（可选，仓库里带了一个合格页与一个反面页）：

```bash
cd test/fixtures && python3 -m http.server 8000
# 另开一个终端
node checker.mjs http://127.0.0.1:8000/good.html          # 退出码 0
node checker.mjs http://127.0.0.1:8000/bad.html --no-fail # 反面例子，看 FAIL 长什么样
```

### 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 没有 FAIL（可能有 WARN） |
| `1` | 有 FAIL |
| `2` | 用法错误 / 网络错误 / 超时 |

### 自动检查覆盖的 12 项

| 清单编号 | 清单项 | 规则 id |
| --- | --- | --- |
| 1.2 | 主标题只有一个主张 | `h1` |
| 1.5 | 手机首屏不被遮挡 | `viewport` |
| 3.1 | 表单字段只留必要项 | `form-fields` |
| 3.2 | 字段有输入提示与校验 | `form-labels` |

| 4.2 | 图片已压缩且指定尺寸 | `image-dimensions` |
| 4.4 | 页面链接全部可用 | `https` |
| 4.5 | 基础 SEO 标签齐全 | `title` / `meta-description` / `canonical` / `meta-robots` / `image-alt` |
| 5.1 | 像素只加载一次 | `script-duplicates` |
| 6.1 | 语言与投放地区匹配 | `html-lang` |
| 7.1 | 隐私说明与免责声明齐全 | `privacy-links` |
| 7.4 | 上线前完整走一遍 | `http-status` |

每一项目前只能判「一部分」：16 条规则的判断边界、37 项完整映射表、规则引擎伪代码、扩展新规则的方法，都在 [`docs/automation.md`](./docs/automation.md)。

### 为什么不做成「全自动」

- **不执行页面 JS**：在别人的页面上跑脚本有安全与隐私风险；代价是动态注入的内容看不到。
- **只请求目标 URL 一次**：不做爬虫、不扫全站、不发 Cookie；代价是页内死链、像素是否真的触发仍要人工或专门工具确认。
- **合规结论必须人签字**：有没有承诺、素材是否合规、信任内容是否真实，机器不能替代人判断。
- **不收集数据、不上传页面内容**：`--json` 只写到 stdout，存不存、传不传由你自己控制。

## 自动 vs 人工

37 项 = **12 项自动（部分覆盖）+ 25 项人工**。建议顺序：

1. 先跑 `node checker.mjs <url>`，把 FAIL 修掉（通常是 https、状态码、title、viewport、noindex 这类硬问题）；
2. WARN 逐条人工确认，不确认的不算过；
3. 再按下面的 37 项清单，把 25 项人工项逐条走完；
4. 都过了再上线。

自动检查是「上线前 5 分钟的机器体检」，不是「一键通过全部检查」。`docs/automation.md` 里写了每一条规则的已知误报，遇到可疑 WARN 先看那张表。

## 1. 首屏 · Above the Fold（6 项）

**1.1 三秒说清「给谁 + 解决什么」**
判断标准：陌生人只看首屏，就知道这是什么、给谁用、能解决哪个具体问题。
不合格怎么改：把「行业 + 产品 + 结果」压进一句主标题，副标题只补一句限定条件，别塞第二个卖点。

**1.2 主标题只有一个主张**
判断标准：标题里只出现一个核心利益点，没有「既……又……还……」。
不合格怎么改：拆成「主标题 + 三条要点」，主标题留最值钱的那一条。

**1.3 主按钮在首屏可见**
判断标准：不滚动就能看到主按钮，文案是动词（立即咨询 / 查看方案 / 获取报价）。
不合格怎么改：收缩首屏高度，把按钮提到标题下方 100px 以内。

**1.4 首屏视觉与业务相关**
判断标准：首图能让目标客户一眼认出「这是给我看的」，不是通用商务图库。
不合格怎么改：换成产品真实界面、真实使用场景，或一张能说明流程的结构图。

**1.5 手机首屏不被遮挡**
判断标准：手机竖屏打开，主标题与主按钮完整可见，不需要横向滑动。
不合格怎么改：给首屏加 `min-height` 断点，图片改用 `object-fit: cover` 并限制高度。

**1.6 慢网下首屏不白屏**
判断标准：网络慢时首屏先出现文字与布局，不会整片空白两秒。
不合格怎么改：图片加 `loading="lazy"` 与显式宽高，字体用系统字体栈兜底。

## 2. 内容与信任 · Content & Trust（6 项）

**2.1 每一屏都有信息增量**
判断标准：删掉任何一屏，读者都不会丢失关键信息。
不合格怎么改：合并重复段落，把「我们很专业」类空话换成具体做了什么。

**2.2 卖点写成可验证的事实**
判断标准：所有数字与结论都能指出来源（公开页面、后台截图、可复现的操作）。
不合格怎么改：删掉无法证实的形容，改成「支持什么 / 包含什么 / 怎么做到」。

**2.3 展示真实的信任要素**
判断标准：展示的是可核对的内容（团队、办公场景、公开案例结构、服务流程），不编造客户名与数据。
不合格怎么改：没有可公开的客户就讲流程与交付边界，讲清「做什么、不做什么」。

**2.4 常见疑问在页面上有答案**
判断标准：费用问询、交付范围、售后方式、时效这四类问题，页面里都能找到答案。
不合格怎么改：加一个 FAQ 区块，用客户原话当小标题。

**2.5 没有夸大与绝对化表述**
判断标准：没有极限化、绝对化的用词，也没有无法兑现的承诺词。
不合格怎么改：换成范围与条件描述，把绝对说法降级成具体做法。

**2.6 段落短、可扫读**
判断标准：每段不超过 3 行，小标题能单独读懂，不靠通读全文。
不合格怎么改：一句一行，长段拆成 2–3 条要点，重点加粗但不超过两处。

## 3. 表单与 CTA · Forms & CTA（5 项）

**3.1 表单字段只留必要项**
判断标准：每个字段都能回答「为什么必须现在填」；能删的先删。
不合格怎么改：先只留「联系方式 + 需求」两个字段，其余等首轮沟通后再补。

**3.2 字段有输入提示与校验**
判断标准：格式错误时即时提示，提示语说明「怎么改」，不是只标红。
不合格怎么改：错误文案写在字段下方，`aria-invalid` 与 `aria-describedby` 一起加。

**3.3 提交后有明确反馈**
判断标准：点击提交后 1 秒内出现加载态，成功后出现下一步说明。
不合格怎么改：按钮切「提交中」并禁用，成功后替换成结果区块，不要只弹一个 toast。

**3.4 主 CTA 在页面中重复出现**
判断标准：至少每两屏出现一次同义主按钮。
不合格怎么改：在长页面的每个信息区块末尾补一个按钮，链接指向同一个锚点。

**3.5 联系方式真实可达**
判断标准：邮箱、表单、客服入口至少一个能正常收到消息，且有人在看。
不合格怎么改：发一条测试消息验证；没有人力值守就先别挂客服入口。

## 4. 技术与速度 · Tech & Speed（6 项）

**4.1 首屏最大内容 2.5 秒内出现**
判断标准：真实网络（非本地）下，首屏最大内容元素 2.5 秒内渲染完成。
不合格怎么改：压缩首图、减少首屏脚本、关键 CSS 内联。

**4.2 图片已压缩且指定尺寸**
判断标准：图片有明确宽高，格式为 WebP / AVIF，单张控制在 200KB 以内。
不合格怎么改：用构建工具批量转格式，加 `srcset` 适配不同屏宽。

**4.3 控制台无报错**
判断标准：打开开发者工具，Console 与 Network 里没有红色报错与 404。
不合格怎么改：逐个修掉资源路径错误，删掉引用了但没用到的脚本。

**4.4 页面链接全部可用**
判断标准：页面上每个链接点开都不是 404，外链也不是死链。
不合格怎么改：上线前用链接检查工具扫一遍，外链加 `rel="noopener"`。

**4.5 基础 SEO 标签齐全**
判断标准：`title`、`description`、`canonical`、`og:image` 齐全，且与页面内容一致。
不合格怎么改：每个页面单独写 title 与 description，别全站复制同一段。

**4.6 有兜底页**
判断标准：错误链接与异常状态有可读的兜底页，并给出回首页的入口。
不合格怎么改：做一个 404 页，放主按钮和一句「可能已经下线」。

## 5. 像素与事件 · Pixels & Events（5 项）

**5.1 像素只加载一次**
判断标准：页面源码里同一个像素脚本没有被重复注入。
不合格怎么改：把像素初始化收到页面顶部统一执行，禁止在组件里二次引入。

**5.2 事件命名统一**
判断标准：事件名与参数表和团队约定一致，大小写与下划线规则固定。
不合格怎么改：先写一张事件表（名称 / 参数 / 触发时机），再按表埋点。

**5.3 关键动作都有埋点**
判断标准：主按钮点击、表单提交、成功页展示都有对应事件。
不合格怎么改：从「用户完成目标」倒推，缺哪一步补哪一步。

**5.4 用调试工具验证过**
判断标准：用平台自带的事件调试工具能看到事件真实上报，参数值正确。
不合格怎么改：本地用调试模式跑一遍，确认事件名与参数没有拼写错误。

**5.5 参数与投放链接对齐**
判断标准：页面能读取到的 `utm_*` 参数，与广告后台里配置的链接一致。
不合格怎么改：统一用一份链接生成规则，投放前抽查三条链接的完整参数。

## 6. 多语言与本地化 · Multi-language & Localization（4 项）

**6.1 语言与投放地区匹配**
判断标准：投哪个地区就默认显示对应语言，不依赖用户手动切换。
不合格怎么改：按浏览器语言做默认，把切换器放在页头显眼位置。

**6.2 翻译是人工校对过的**
判断标准：没有明显机翻痕迹、没有中英混排、没有同一名词两种译法。
不合格怎么改：核心页面的标题、按钮、错误提示必须人工过一遍。

**6.3 数字、日期、货币格式符合当地习惯**
判断标准：日期顺序、货币符号、电话区号都按目标市场书写。
不合格怎么改：用 `Intl.DateTimeFormat` 与 `Intl.NumberFormat` 本地化，别手写字符串。

**6.4 长语言不撑破布局**
判断标准：德语、俄语这类长语言下，按钮与标题不换行挤出容器。
不合格怎么改：按钮给 `white-space: nowrap` 之外的弹性空间，容器用 `min-width: 0`。

## 7. 合规与上线 · Compliance & Launch（5 项）

**7.1 隐私说明与免责声明齐全**
判断标准：页面上有隐私说明和免责声明的入口，且能正常打开。
不合格怎么改：放页脚固定链接，内容只写事实与边界，不写承诺。

**7.2 没有任何结果承诺**
判断标准：全站找不到对审核结果、投放效果或收益的承诺类表述。
不合格怎么改：把承诺改成「我们负责做什么」，把结果交给平台规则与实际执行。

**7.3 不出现受限类目内容**
判断标准：公开页面不放受限类目的素材、截图与案例。
不合格怎么改：只展示电商、工具、应用下载这类合规案例，截图里的客户信息打码。

**7.4 上线前完整走一遍**
判断标准：从广告链接点进来，到提交成功，全程无断点、无死链、无疑问卡点。
不合格怎么改：用手机真机 + 弱网各走一遍，记录每一步耗时。

**7.5 有回滚与备份**
判断标准：上线前的版本有备份，出问题能在 10 分钟内切回。
不合格怎么改：发布前打一个 tag 或导出静态文件，写清回滚步骤。

## 常见问题 · FAQ

**37 项都要一次做完吗？**
不用。先做「首屏」「表单与 CTA」「技术与速度」三组，收益最直接；剩下的按上线节奏补。

**没有设计/开发也能用吗？**
能。每一项写的是「判断标准」和「怎么改」，不依赖具体工具；用模板 + 可视化编辑也能逐项对。

**可以改成团队自己的版本吗？**
可以，MIT License，复制成内部文档即可；建议保留「判断标准」这一列，否则会变成打勾走形式。

**自动检查器能替我把 37 项都检查完吗？**
不能。它只覆盖 12 项、共 16 条规则，剩下 25 项（信任内容、合规结论、翻译质量、真机走查等）必须人工判断。自动检查 PASS 只是「机器能看的这几项没硬伤」，不等于可以上线。
